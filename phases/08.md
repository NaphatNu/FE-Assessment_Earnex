## Why this phase exists

Phase 01 pinned a data contract that the implementation then quietly departed from:
the asset path, five field names, the repository's type, and its test seam all differ,
and one data invariant is violated while the test that was supposed to catch it was
rewritten into a snapshot that blesses the violation. This phase makes code and contract
agree again. Nothing here is a new decision — it is the phase-01 decision, applied.

## Task 3 — repository shape

`lib/data/traders_repository.dart`:

```dart
abstract interface class TradersRepository {
  Future<List<Trader>> fetchTraders();
}

class AssetTradersRepository implements TradersRepository {
  AssetTradersRepository({AssetBundle? bundle}) : _bundle = bundle ?? rootBundle;

  final AssetBundle _bundle;

  @override
  Future<List<Trader>> fetchTraders() async { ... _bundle.loadString('assets/mock/traders.json') ... }
}
```

`abstract interface class` (not `abstract class`) and the injectable `bundle` were both in
the phase-01 order. The body keeps its current decode/map logic, unchanged apart from the
bundle and the path.

## Task 4 — restore the violated data invariant

`High Risk` is carried by 2 traders; the contract is **at least 3 per tag**. Fix by adding
`"High Risk"` to **`t002` (`師429`)** — and to that trader only. It is the right one on the
data's own terms: `mdd30d` 6.97 is the third-highest in the file and `sharpe` 0.85 is the
weakest of every non-negative Sharpe. Do not touch its numbers, and do not touch any other
trader.

After the edit the file must still satisfy, all at once:

- exactly 18 traders, `id` unique
- every tag is one of the 8: `Top Performer`, `Money Maker`, `Most Resilient`,
  `Whale Manager`, `Solid Growth`, `Low Leverage`, `Most Consistent`, `High Risk`
- every trader carries 1–3 tags, and at least one trader carries 3
- every tag is carried by **≥ 3** traders
- for every unordered pair of distinct tags, the OR-match count is **5–9**

(That exact edit has been verified to satisfy all five. If a test still fails, the bug is in
the test, not in the choice of trader — re-read the invariant list before changing data.)

## Task 5 — turn the data test back into an invariant test

Rename `test/data/mock_data_test.dart` → `test/data/traders_json_test.dart` and rewrite its
body so that every assertion is one of the five invariants above, **computed from the file**.

Delete the `expectedTagCounts` map and the `expectedTags` equality assertion: hardcoding the
per-tag totals turned a contract check into a change-detector that reported green while
`High Risk` sat at 2. The allowed-tag check stays, but as a subset check
(`allTags.difference(allowed)` is empty) plus the `≥3` count rule — not as an exact-count map.

Keep reading the file through `dart:io` `File`, not `rootBundle`.

## Task 6 — prove the injected bundle works

New `test/data/traders_repository_test.dart`:

```dart
class _FakeAssetBundle extends AssetBundle {
  _FakeAssetBundle(this.contents);
  final String contents;

  @override
  Future<ByteData> load(String key) async =>
      ByteData.sublistView(Uint8List.fromList(utf8.encode(contents)));
}
```

(`AssetBundle.loadString` is implemented on top of `load`, so overriding `load` is enough.)

Two tests:
1. `AssetTradersRepository(bundle: _FakeAssetBundle(<a 1-trader JSON array>))` returns one
   `Trader` with every field parsed correctly — this is the seam phase 01 asked for.
2. A malformed payload (`'not json'`) makes `fetchTraders()` throw — the error path
   `tradersProvider` surfaces as `AsyncError`.
